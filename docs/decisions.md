### ADR-0001 · 对齐用推理，不用数值打分

**状态**：Accepted · 2026-06

**背景**：维度澄清需要排序"先问什么"。一种做法是给每维算"影响力 × 模糊度"分。
**决策**：不打任何数值分 / 置信度。维度用定性状态（open/leaning/resolved/conflicting/blocked_by），由 LLM 推理判断问什么、何时收敛。
**理由 / 影响**：LLM 不擅长算术，该分主观且伪精确。换来更稳的定性推理；收敛靠确定性谓词（见 ADR-0003）补稳定性。

### ADR-0002 · 设计空间为唯一审美与知识来源

**状态**：Accepted · 2026-06

**背景**：阶段二的"导演声音 / 多样性"从哪来？
**决策**：不写死导演人格 / 风格卡；A/B/C 方向从召回范例**归纳**而来，数量由数据决定（≤3，不硬凑）。
**理由 / 影响**：写死人格注入的是训练集刻板印象，且丢掉范例携带的、针对具体意图的电影知识。系统多样性来自数据；配合飞轮自增长。**铁律：意图忠实 > 范例原貌。**

### ADR-0003 · 收敛 = 黏滞要紧集 + LLM 定性推理（不打分）

**状态**：Accepted · 2026-06

**背景**：原稿把收敛判据设计为确定性谓词（纯代码），2026-06 经决策者确认改为 LLM 定性推理。
**决策**：
orchestrator 显式维护「要紧维度集」（黏滞，只在新证据下增删）；收敛是其上的 LLM 定性推理判据。
LLM 接收当前 dimension states + 对话历史 → 推理出 converged/not converged。
**不打任何数值分**。维度状态仍维持定性标签（open/leaning/resolved/conflicting/blocked_by），LLM 据此做整体判断。
**理由 / 影响**：
- "LLM as judge" 能理解对话上下文和维度之间的语义关系——"用户说'差不多就这样吧'暗示可以收敛了"，纯代码判据捕捉不到这种信号。
- 但机制框架保留黏滞要紧集 + interrupt + confirm 门控，防止 LLM 过早放行。
- 收敛后必须 interrupt(confirm) 让用户确认，双重保险。

### ADR-0004 · 编排用 LangGraph

**状态**：Accepted · 2026-06

**背景**：需要带共享状态的状态机 + 多轮人在环 + 并行 + 循环。
**决策**：用 LangGraph `StateGraph`；放弃 CrewAI / AutoGen。
**理由 / 影响**：本设计要的是*确定性受控*编排（显式收敛谓词、显式路由），与 CrewAI/AutoGen 的"自治涌现"模型相悖。LangGraph 的 `interrupt` + checkpointer 恰好支持可暂停 / 可恢复的人在环。轻量替代 Pydantic AI 备选；一次性原型可手搓。

### ADR-0005 · 技术栈 Python + FastAPI + Postgres/pgvector + React

**状态**：Accepted · 2026-06

**背景**：后端是多 agent 编排 + 混合检索，前端是服务端驱动的动态 widget + 结构化脚本编辑。
**决策**：后端 Python（FastAPI + LangGraph），存储 Postgres + pgvector（一库三用：checkpoint + 向量 + tags 过滤），前端 React + Vite，类型经 OpenAPI 生成。
**理由 / 影响**：核心在 agent 编排 + HITL 持久化 + 检索 / ML 生态，Python 最强。代价：跨语言边界靠生成 TS 类型对齐 widget 协议。详见 [`/架构设计.md`](../架构设计.md)。
**LLM**：开发阶段用 DeepSeek V4 Flash；生产阶段换 Claude Opus / Qwen 3.6 Plus。

### ADR-0006 · 十参数为镜头实例标准

**状态**：Accepted · 2026-06

**背景**：本体每叶原本挂 7 个摄影列（景别/角度/构图/运镜/光影/色彩/焦距）；镜头脚本是十参数（多 景深/节奏/时长）。
**决策**：本体技法列从 7 补至 10（增加 景深/节奏/时长），与 ShotScript 十参数完全对齐。"两个高度"不再区分。
**理由 / 影响**：消除概念歧义，减少维护两套参数的认知负担。唯一代价：景深/节奏/时长 在叶子级有默认值时可能偏粗，但在缺少范例的冷启动期这反而是优势（提供初始方向）。

### ADR-0007 · 本体元字段落定

**状态**：Superseded by ADR-0010 · 2026-06

**背景**：ontology-spec 列出 4 个缺失元字段，系统运行必需。
**决策**：
- `control_nature`：注意力引导=single, 距离感知=scale, 运动与节奏=multi(内部分运动/节奏两子轴,各渲染为滑块), 情绪唤起=multi, 氛围营造=single, 共情引导=multi, 信息控制=multi, 期待引导=single, 因果建构=single, 视角控制=single, 意义阐释=multi
- `scale` 端点：距离感知=[亲密,个人,社会,公共]; 运动特性子轴=[静止,舒缓,适度,剧烈]; 节奏特性子轴=[极缓,舒缓,适中,急促]
- `blocked_by_default`：见 ontology-spec 推理表，作为**排序建议**（align agent 参考但不硬性遵守）
- `constraints`：mutex/pairs 基准表，作为 critic 意图忠实检查基线

### ADR-0008 · 方案库不灌种子，全由飞轮自增长

**状态**：Superseded by ADR-0010 · 2026-06

**背景**：架构设计 M2 原计划手灌 ~20 条种子范例；但 final_proposal 的设计中方案库从空开始。
**决策**：遵循 final_proposal 原始设计——方案库初始为空。冷启动期间召回永远返回 `signal=empty`，全走 OOD 兜底路径（LLM 基于电影语法第一性原理生成，标低置信）。signal 机制（rich/thin/empty）待库有一定规模后再引入。
**影响**：M2"召回"里程碑重新定义：只需实现 pgvector 混合检索基础设施 + 飞轮回写，不要求种子数据。架构设计的"手灌 ~20 条"行删除。

### ADR-0009 · Critic 耦合规则：硬编码规则表 + LLM 判定

**状态**：Accepted · 2026-06

**背景**：参数耦合检查（十参数三组兼容性）是纯电影物理知识，而"意图忠实"是语义判断，处理方式不同。
**决策**：混合模式——三组耦合的基本兼容规则硬编码为规则表（空间组：景别+焦距+景深+构图+角度的兼容矩阵；时间组：运镜+节奏+时长的协调表；影调组：光影+色彩的基本和谐规则）；意图忠实检查由 LLM 判定。
**理由**：耦合规则是确定的物理/电影知识（长焦×广角必然冲突），硬编码比 LLM 判更稳更快。意图忠实是语义问题，只能 LLM 判。

### ADR-0010 · 本体 v3 + 纯推理为生成基线，检索降级为可选增强

**状态**：Accepted · 2026-06

**背景**：
原方案的知识来源是"标注数据 → 检索召回范例 → 策略归纳"。但 ADR-0008（库不灌种子）叠加本体十技法列全空，意味着冷启动期系统的事实运行路径一直是"无范例的 LLM 裸推理"——架构上存在的召回链路实际虚设，且无人为这条暗路做过设计。同期分类法升级为 v3（`labels_v3.json`：12 一级 × 56 二级，带 A/B 类型、双极轴、维度值集、作用域与 7 组易混淆判别规则）。

**决策**：
1. **本体切换 v3**：`labels_v3.json` 为分类内容权威源；`meta_v3.yaml` 显式化元字段（A/B 类型、双极轴、值集、作用域、易混淆规则）；`knowledge_v3.yaml` 为 56 个二级意图各挂一张电影语法知识卡（机制 + 候选手法 + 经典参照）。三源由 loader 合并校验。ADR-0007 的 control_nature/blocked_by_default/constraints 元字段体系由此取代。
2. **纯推理为生成基线**：生成沿三层推理链——B 类效果意图（要观众感到什么）→ 心理/知觉机制（知识卡）→ A 类构成意图（画面怎么安排）→ 十参数。方向多样性来自"主导机制族不同"，由设计空间结构保证；范例锚定（anchored_exemplars）替换为机制锚定（mechanism + dominant_intents + 每镜 serves）。
3. **检索降级为可选增强**：recall/induction 节点从主路径摘除，pgvector 基础设施与飞轮回写保留。strategy 节点尽力查询方案库，命中则作为附加参考注入，失败或为空不阻塞、不降级。库经飞轮长起来后增强自然生效。
4. **知识卡取代数据标注**：把"标注大量镜头实例"换成"为 56 个叶子精修知识卡"（LLM 初稿 + 人工审校），知识挂在分类法本身上，使"设计空间是唯一知识来源"（ADR-0002）重新成立。

**理由 / 影响**：
- 解决 ADR-0002 与 ADR-0008 的张力：库空 + 先验列空时，唯一知识来源其实是 LLM 训练集，恰是 ADR-0002 要避免的；知识卡 + 机制链让推理有据可审。
- v3 的 A/B 标注天然给出效果→手段的推理脚手架（信息管理 8.1=A 与 8.2-8.4=B 的混合标注印证该语义）；易混淆判别规则免费充当对齐探针与 critic 检查。
- Critic 加重：新增确定性 serves-code 检查、易混淆误用与双极轴自洽判定（与 ADR-0009 的耦合规则表并行）。
- ADR-0002 表述修订："A/B/C 方向从召回范例归纳" → "方向从设计空间的机制路径枚举而来"；铁律改写为**意图忠实 > 手法华丽**。
- ADR-0008 的"不灌种子"保留，"冷启动全 OOD 兜底"的表述废止——纯推理不是兜底，是设计过的基线。

### ADR-0011 · 参考基底图贯穿会话 + 镜头帧渲染接入点

**状态**：Accepted · 2026-06

**背景**：
产品形态升级：用户在会话起点可上传一张参考画面,后续镜头设计在这张图的基础上展开;
下一阶段将接入生图 API,以该图为 base、用图像编辑逐镜渲染镜头序列呈现给用户。

**决策**：
1. **上传通道**：`POST /sessions` 同时支持 JSON(纯文本)与 multipart(文本 + 图);图片存
   `backend/uploads/`(gitignore),经 `/api/uploads/{file}` 静态服务;`SessionState.reference_image`
   贯穿全会话,所有 TurnResponse 携带,前端各阶段常驻展示。
2. **视觉理解可降级**：`LLM_VISION_MODEL`(留空则尝试主模型)对基底图产出一段客观画面描述
   `image_brief`,注入对齐/收敛/策略/生成四处 prompt;VLM 不可用时静默降级为纯文本流程,不阻塞。
3. **基底连续性约束**：有基底图时,strategy 的方向枚举与 generate 的镜头设计必须以基底画面的
   主体与场景为出发点(机位/光线/节奏可变,主体与空间不可凭空更换)。
4. **渲染接入点(契约预留)**：`Shot` 新增两个字段——
   - `frame_edit_hint`:从基底图到本镜画面的图像编辑指令(有基底图时由 generate 沿机制链产出,
     一两句、可被图像编辑模型直接执行);
   - `frame_image`:渲染帧 URL,生图 API 接入后填充(渲染产物同样落 uploads/)。
   生图 API 接入时只需新增一个渲染服务消费 `frame_edit_hint`,不动生成链路。

**理由 / 影响**：
- 画面线索(主体/空间/光线)是天然的对齐证据,可减少提问轮次;基底连续性让"同一意图的
  不同机制路径"在视觉上可比较。
- `frame_edit_hint` 把"镜头参数 → 可执行的图像编辑指令"的翻译放在 generate 内完成,复用三层
  机制链上下文,比事后由渲染服务自行解读十参数更忠实。
- 全链路对"无图会话"保持零损耗兼容(JSON 路径、prompt 不注入、hint 留空)。

### ADR-0012 · 关键帧渲染接入 + 重拍摄语义(输入必须带图)

**状态**：Accepted · 2026-06

**背景**：
ADR-0011 预留的渲染接入点正式接入。网关可用生图模型:qwen-image-2.0(-pro)、wan2.7-image(-pro)。
产品语义同步明确:会话**必须**以一张参考画面开始,整个流程是为这张画面设计**重拍摄方案**——
画面只用于解析内容(主体与空间锚定),拍摄风格(光线/色调/机位/景别/节奏/氛围)完全服从用户意图,
允许与原画面气质截然不同(如喜剧画面改作恐怖片拍法)。**用户的需求是最终决定点。**

**决策**：
1. **输入必须带图**:`POST /sessions` 仅接受 multipart(raw_intent + image);无图返回 422。
2. **重拍摄语义贯穿 prompt**:基底画面解析段落明确"画面只锚定主体与空间,风格服从意图";
   对齐 agent 不得从画面现状脑补情绪/氛围维度(画面现有氛围只是现状,不是用户意图证据);
   frame_edit_hint 改为【重摄指令】,"需要剧变就大胆剧变"。
3. **渲染服务**(`app/render.py`):经网关 `/chat/completions` 的 DashScope 原生多模态协议
   (content 用 `{"image": dataURL}` + `{"text": 指令}` 键,响应 `output.choices[0].message.content[0].image`
   为带时效 OSS URL,立即下载落盘 uploads/)。`IMAGE_MODEL` 可配置,默认 qwen-image-2.0;
   编辑模式输出自动保持基底图宽高比。
4. **`POST /sessions/{id}/render {scheme_id}`**:逐镜渲染(并发上限 2,单镜失败不阻塞其余),
   指令优先用 frame_edit_hint、缺失时由十参数合成。**渲染产物不写图状态**——实测
   `aupdate_state` 会清掉挂起的 interrupt(后续 resume 全部 409);改为以 uploads/ 落盘文件为
   事实存储(文件名确定性 `{session}_{scheme}_s{order}.png`),TurnResponse 构建时
   `hydrate_frames` 运行时合并 `frame_image`。渲染是纯工具调用,图状态零接触。
5. **按需渲染**:渲染由用户在候选页逐方案触发(成本控制),编辑后可重渲。

**理由 / 影响**：
- 概念验证:冷蓝夜景基底 + "暖橙黄昏"指令 → 构图/主体/窗光完整保留、色调彻底转换,
  确认 qwen-image-2.0 编辑能力满足"主体锚定 + 风格剧变"。
- 对齐语义修正很关键:此前"画面氛围线索可作维度证据"的提示在重拍摄场景下是反模式
  (用户上传喜剧图想拍恐怖时,系统不能顺着画面现状收敛)。
- OSS URL 带时效 → 渲染产物必须立即下载并自托管(uploads/),与基底图同生命周期。
